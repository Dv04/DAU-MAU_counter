## Strengthener 1 — history-independence exhibit

**Definition under test** (paper, Definition "History-Independent Deletion"): a state
backend supports history-independent deletion if, for input multiset D and user token
`u`, the backend state after ingesting D then executing `remove(u)` is identically
distributed to the state after ingesting D∖{u} directly.

**Method:** for each backend, many random trials of: build `S_full` from a randomly
shuffled D, delete `u` via `S_full.a_not_b({u})`; separately build `S_direct` from a
*independently* shuffled D∖{u}; compare canonical retained state (exact key/hash/int
set) and `estimate()`. `k=16` sweeps both `n≤k` (no bottom-k truncation possible) and
`n>k` (truncation occurs) regimes cheaply; a second sweep uses the shipped production
default `k=4096` at `n=20000` to confirm the effect isn't a small-`k` toy artifact.

|---|---|---:|---:|---:|---:|---:|

| set | n>k (truncation occurred) | 1200 | 1.0000 | 1.0000 | 0.0000 | 0.0000 |
| set | n>k (production k=4096) | 60 | 1.0000 | 1.0000 | 0.0000 | 0.0000 |

**Theta:** not tested. No Theta sketch implementation exists anywhere in this
repository, committed or uncommitted. The paper's reference-architecture prose names
it as a "viable probabilistic backend," but there is no code to run. This is reported
as N/A rather than assumed or simulated.

### Interpretation (honest, both directions)

- **`set` (the shipped, tested exact backend): exactly matches in 100% of 2,460
  trials**, across every regime, with zero estimate divergence ever observed. This
  empirically confirms the paper's "exact backend satisfies history-independence
  unconditionally" claim, on the actual code that ships.
- **`kmv` (the shipped, tested approximate backend): matches unconditionally only in
  the `n≤k` regime (1200/1200 = 100%), and diverges roughly a third to a quarter of
  the time once truncation occurs (`n>k`: 64.67% match at small k, 76.67% at
  production k=4096, both n>k).** The mechanism is exactly the one the paper's prose
  anticipates: `KMVSketch.add()` permanently discards hashes once more than `k` have
  been seen (`while len(self._hashes) > self._config.k: removed = self._hashes.pop()`
  in `src/dp_core/sketches/kmv_impl.py`, no auxiliary buffer of displaced candidates is
  kept), so `a_not_b()`-based deletion of a retained element cannot "re-admit" the
  candidate that was evicted earlier — the paper's own stated condition for KMV/Theta
  history-independence ("deletion must fully restore the sketch to the state it would
  have reached without the deleted element, including re-admitting displaced
  candidates — which standard implementations meet by retaining sufficient auxiliary
  state") is **not met by this repo's shipped KMV implementation**. This is a genuine,
  reproducible, non-trivial divergence (mean cardinality error 10.4, up to 302.9 in the
  worst case at small k; up to 16,370 at production k=4096/n=20,000 — the estimator's
  own `(k-1)/threshold` formula amplifies the missing-one-hash truncation into a larger
  cardinality swing). This is a **negative, paper-usable result** exactly as the task
  anticipated: it should be cited as direct empirical support for the paper's own
  "conditional" claim about KMV/Theta, and as a concrete implementation caveat (the
  shipped KMV is the naive, non-history-independent variant, not the "standard
  implementation with auxiliary state" the paper's Definition discussion alludes to as
  the condition under which KMV *would* qualify).
- **`roaring` (orphaned/uncommitted snapshot): matches exactly in 100% of 2,460
  trials**, consistent with it being deletion-native (direct bitmap subtraction, no
  sampling/eviction). This is the ONLY evidence in this repository that a Roaring-based
  exact backend behaves as the paper describes — and it comes from code that has never
  been committed or tested. Take it as a plausibility check on the *design*, not as
  validation of anything currently shipped.

## Strengthener 2 — tree-aggregation vs. per-release composition (365-day horizon)

### Part B — analytical, using the repo's real ε/δ/sensitivity and its actual RDP code

Computed by literally calling `PrivacyAccountant._best_from_curve` (the exact function
the accountant uses to convert an RDP curve to (ε,δ)-DP) with a synthesized 365-release
RDP curve, not by hand-derived formulas alone. Sensitivity = `min(w_bound,1) = 1`
(shipped default `w_bound=2`). Tree levels `L = ceil(log2(365)) + 1 = 10`.

| Mechanism | Per-release constant | Shipped composition rule | Cumulative ε after 365 releases (shipped rule) | Per-release noise stdev (shipped) | Tree-agg total budget needed to match the *same* per-release stdev | Tree-agg per-release stdev at the *same* cumulative-365-day budget |
|---|---|---|---:|---:|---:|---:|
| DAU (Laplace, δ=0) | ε=0.3 | naive summation (δ≤0 ⇒ RDP path skipped) | 109.5000 | 4.7140 | **9.4868** | 0.4084 |
| MAU (Gaussian, δ=1e-6) | ε=0.5 | RDP composition via `_best_from_curve` | **11.1051** (naive-sum reference only: 182.5000) | 10.5976 (σ) | — *(see note)* | worst-case 5.5470 / best-case (day 1) 1.7541, at per-level σ=1.7541 chosen to match the shipped mechanism's own 11.1051 cumulative RDP-composed ε over the same 365 releases |

**Key DAU number:** the shipped per-release DAU mechanism achieves noise stdev 4.71 on
*every* release, but its true cumulative privacy cost after a year of daily releases is
ε≈109.5 (basic/naive composition, since δ=0 disables the RDP path entirely — see
`PrivacyAccountant.budget_snapshot`). A tree-aggregation mechanism could deliver the
**same 4.71 per-release accuracy for a fixed total budget of only ε≈9.49** — an
**~11.5×** reduction in the cumulative privacy cost for identical accuracy — or,
inverting it, spending the *same* 109.5 total via tree-aggregation instead would buy
**~11.5× lower noise per release** (stdev 0.41 vs 4.71).

**Key MAU number, and an honest surprise:** the shipped Gaussian/MAU mechanism already
uses proper RDP composition, and it is *much* tighter than naive summation on its own
merits — 365 daily Gaussian releases compose to ε≈11.1 via RDP, vs ε≈182.5 if summed
naively (a ~16.4× improvement the paper's own accountant already provides, independent
of tree-aggregation). Tree-aggregation still helps further (matching that same ε≈11.1
budget via a 10-level tree instead of 365 flat releases lets each level use a larger
per-level σ=1.75 instead of the shipped σ=10.60, i.e. releases touching few tree nodes —
day 1 touches 1 node — could be **~6× more accurate**, stdev 1.75 vs 10.60), but the
*relative* gain over the shipped mechanism is smaller for MAU than for DAU, precisely
*because* the shipped mechanism's own RDP composition is already doing a good job for
the Gaussian case. **This asymmetry (large win for the pure-DP/Laplace/DAU path,
smaller but still real win for the already-RDP-composed Gaussian/MAU path) is itself an
honest, useful finding for the Limitations discussion** — the paper's reviewers'
concern about long-horizon correlated noise applies with full force to DAU, and with
reduced (but non-zero) force to MAU, exactly because of a composition-rule asymmetry
already present in the shipped accountant.

### Part A — empirical Monte Carlo validation (on a synthetic additive proxy, disclosed)

**Important substitution, disclosed up front:** DAU/MAU are non-additive
distinct-count (union) queries; classical binary-tree aggregation (Chan–Song–Shi /
Dwork–Naor–Pitassi–Rothblum) is defined for *additive* SUM/COUNT queries and does not
directly decompose a union query through a summation tree. Rather than fabricate a
"tree-aggregated cardinality sketch" (a nontrivial research construction beyond this
task's scope), Part A empirically validates the noise-growth *formulas* underlying
Part B's analytical claims — using the repo's own `sample_laplace()` primitive and its
real `epsilon_dau=0.3` default — on a synthetic additive daily counter (new-user
arrivals), at a total privacy budget matched to what the shipped DAU mechanism already
accumulates over 365 days (ε_total = 365 × 0.3 = 109.5). 800 Monte Carlo trials, seed
20260708.

| Day | Naive (fixed ε_total/365 per release) RMSE | Tree-aggregation (same ε_total, 10 levels) RMSE | Tree/naive ratio |
|---:|---:|---:|---:|
| 1 | 4.6232 | 0.1326 | 0.0287 |
| 92 | 4.7092 | 0.2564 | 0.0544 |
| 183 | 5.0394 | 0.3245 | 0.0644 |
| 274 | 4.4472 | 0.2196 | 0.0494 |
| 365 | 4.6151 | 0.3225 | 0.0699 |

Closed-form cross-check (not Monte Carlo): per-release naive stdev 4.7140, tree stdev
0.1292 (day 1, touches 1 node) to 0.4084 (worst case, touches all 10 levels) — the
empirical RMSEs above track these predictions closely (e.g. day 1: 0.1326 empirical vs
0.1292 predicted; day 365, which touches 6 tree nodes given `popcount(365)=6`: 0.3225
empirical vs a recomputed √6 prediction of 0.3164 — consistent within Monte Carlo
noise).

**Reading this table correctly:** the "naive fixed ε_total/365 per release" scheme
computed here is, by construction (ε_total was set to exactly `365 × epsilon_dau`),
numerically identical to the shipped per-release scheme's own per-release accuracy —
this is deliberate, not a bug: it lets the *empirical* simulation reproduce the same
"same total budget, compare accuracy" comparison as Part B's DAU row, using actual
random sampling rather than only closed-form algebra. It confirms, empirically, that
spreading the same fixed total budget across only 10 tree levels instead of 365 flat
releases gives roughly **14–35× lower error** (computed from the five sampled days'
ratios: 34.9×, 18.4×, 15.5×, 20.2×, 14.3× at days 1/92/183/274/365 respectively) for
reconstructing cumulative/prefix-style
aggregates — consistent with Part B's ~11.5× figure for the (different, worst-case
vs.-typical) framing used there.

## Bottom line for the revision response

1. **History-independence (Strengthener 1) is now backed by a real, reproducible,
   negative-and-positive result on the shipped code**: `set` is unconditionally
   history-independent (2,460/2,460 trials); the shipped `kmv` is only conditionally so,
   and the condition (`n ≤ k`) is exactly the one the paper's Definition anticipates —
   caught empirically, not asserted. Theta cannot be tested (doesn't exist in the repo).
   Roaring can only be tested from orphaned, uncommitted code — flag this to whoever
   owns the paper's evaluation-section claims before submission.
2. **Tree-aggregation (Strengthener 2) shows a real, quantified, order-of-magnitude
   improvement for the DAU (Laplace) path** at a matched long-horizon privacy budget
   (~11.5× in the analytical framing, ~14–35× in the empirical-on-a-proxy framing,
   depending on which "matched" definition and which day is used) — directly
   supporting the reviewers'/our own Limitations note. **The improvement is real but
   smaller for the MAU (Gaussian) path**, because the shipped accountant already does
   proper RDP composition there; this nuance is worth stating precisely rather than
   claiming a uniform win.
