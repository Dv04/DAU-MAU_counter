\begin{abstract}
We present a prototype implementation and experimental evaluation of a differentially private (DP) system for computing Daily Active Users (DAU) and Monthly Active Users (MAU) that handles user deletion requests under GDPR-style ``right to be forgotten'' regulations. 

Our system combines deletion-friendly KMV (K Minimum Values) sketches with user-level differential privacy mechanisms, achieving relative errors below 2\% at practical privacy levels ($\varepsilon \le 1.0$) on our test workloads. We demonstrate that our approach removes deleted users from historical aggregates through explicit tombstone events that propagate retroactively to all affected days. Additionally, we provide a privacy budget accounting system using Rényi Differential Privacy (RDP) composition for tight multi-release guarantees.

Experimental results on synthetic workloads with up to 10,000 users over 30 days suggest that the approach achieves favorable accuracy-privacy-deletion tradeoffs. Our implementation includes a FastAPI REST service, a command-line interface, and test coverage of 82\% (33 tests). The system handles adversarial deletion patterns while maintaining privacy guarantees, demonstrating feasibility for GDPR-compliant user counting.
\end{abstract}

\section{Problem Description}
%==============================================================================

Modern online services and IoT platforms routinely track distinct daily active users (DAU) and monthly active users (MAU) to monitor growth, retention, and product health. DAU measures the number of unique users active on a given day, while MAU counts users active within a rolling window of days (typically $W = 30$). In practice, activity arrives as a high-volume stream of events, and realistic systems must comply with privacy regulations such as GDPR and CCPA, which grant users a \emph{right to be forgotten}. This means that once a user requests erasure, their contribution must be retroactively removed from all relevant aggregates---not just future counts, but historical days as well.

We model user activity as a \emph{turnstile stream} of positive and negative events. A positive event $+u@d$ indicates that user $u$ was active on day $d$, while a negative event $-u@d$ encodes a deletion request to remove $u$ from the counts for one or more days. The system must continually release DAU and MAU estimates:
\[
\text{DAU}(d) = \bigl|\{u : u \text{ active on day } d\}\bigr|, \quad
\text{MAU}_W(d) = \bigl|\{u : u \text{ active on some day in } [d-W+1,d]\}\bigr|
\]
with differential privacy guarantees, meaning that published counts should not reveal information about any single user.

\paragraph{Concrete Example.} Consider an app with $N=10{,}000$ daily users, of which 5\% request deletion mid-month. A naive distinct-count system without deletion support would overestimate MAU by hundreds of users, potentially violating privacy laws. Furthermore, a system that ignores differential privacy could leak information through the sequence of daily releases---an adversary observing a sudden jump in DAU could infer that a specific individual became active. Our goal is to maintain accurate, private estimates of DAU/MAU even under such deletion requests.

\paragraph{Real-World Stakes.} Accurate, privacy-preserving tracking of DAU and MAU under deletions is critical for large apps that must obey GDPR-style "right to be forgotten" regulations, while still making business decisions based on reliable metrics. Failure to respect deletions can lead to legal penalties (fines up to 4\% of global revenue under GDPR) and loss of user trust. Our system addresses this by:
\begin{enumerate}[leftmargin=*]
    \item Using cryptographic hashing with epoch-stable salts to pseudonymize users while enabling correct MAU deduplication across days;
    \item Writing explicit "tombstone" events for deletions that propagate to all affected historical days;
    \item Adding calibrated Laplace (for DAU) or Gaussian (for MAU) noise with user-level sensitivity analysis;
    \item Tracking cumulative privacy loss via an RDP-based accountant with monthly budget caps.
\end{enumerate}

The technical challenge arises because classical differential privacy analysis assumes monotone streams (only insertions) or simple counters. Distinct counting under deletions violates standard sensitivity bounds, and naive DP mechanisms can produce biased or overly noisy estimates. Our project explores combining deletion-friendly streaming sketches (KMV) with user-level DP mechanisms to yield accurate, privacy-preserving DAU/MAU estimates that respect all deletion requests.

\section{Literature Survey}
%==============================================================================

Our project builds on two main pillars from the course: streaming distinct-count estimation and differentially private algorithms under continual observation.

\subsection{Streaming Distinct Counting}

Classic work by Flajolet and Martin on probabilistic counting \cite{flajolet1985probabilistic} and its later refinement HyperLogLog (HLL) \cite{flajolet2007hyperloglog} introduced bit-pattern based sketches for estimating the cardinality of large sets from streaming data. These sketches are mergeable (supporting unions across shards) and provide tight relative error guarantees using sublinear memory. Specifically, HyperLogLog achieves a standard error of approximately $1.04/\sqrt{m}$ using $m$ registers, typically requiring only $O(\log \log n + \log(1/\delta))$ bits per register for $n$ distinct elements under failure probability $\delta$.

However, HLL is essentially append-only: registers store maxima, and there is no native support for removing a user once its contribution has been merged. More recent systems work, such as Apache DataSketches Theta sketches \cite{datasketches2024theta}, represent sets via bottom-$k$ sampling. Theta sketches support union and set difference (A-not-B), making them naturally better suited to model deletions and rolling windows in a turnstile setting. The KMV (K Minimum Values) sketch is a closely related structure that maintains the $k$ smallest hash values, enabling both cardinality estimation and set operations.

\subsection{Differential Privacy for Continual Release}

Classical DP mechanisms for counters and histograms under continual observation use tree aggregation or binary mechanisms to release noisy partial sums over time while controlling privacy loss through composition \cite{dwork2010differential}. Specifically, Dwork et al. add Laplace noise to aggregated counts at each node of a binary tree, ensuring that the total noise scales logarithmically with the number of releases while preserving user-level privacy. These methods work well for numeric aggregates with bounded per-user sensitivity, but they assume monotone contributions or simple add-only updates.

Recent theoretical work on DP distinct counting in turnstile streams introduces the notion of \emph{flippancy} $w$, defined as the maximum number of times a single user's indicator can flip between "present" and "absent" over the entire time horizon \cite{jain2023counting}. Jain et al. achieve user-level DP by scaling noise according to each user's flippancy, allowing continual release of distinct counts even in the presence of deletions. These results show that if $w$ is small---for example, if we coalesce events so that each user/day contributes at most one insertion and one deletion---then it is possible to achieve user-level DP with additive error on the order of $O(\sqrt{w} \cdot \text{polylog}\, T)$, where $T$ is the number of releases.

Complementary work studies space-efficient DP algorithms for turnstile distinct counting, emphasizing sublinear memory and worst-case lower bounds for event-level DP in this setting \cite{cummings2025differentially}.

\subsection{Deletion Handling in Production Systems}

Real-world analytics platforms handle deletions through various mechanisms, none of which provide the combined guarantees we target:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Google Analytics:} Uses pre-aggregated rollups that cannot easily support retroactive deletion. GDPR requests are handled by marking data for exclusion in future reports and scheduling offline re-aggregation jobs \cite{datacalculus2023}.
    
    \item \textbf{Snowflake/BigQuery:} Support ``time travel'' queries that can reconstruct historical states, enabling deletion by recomputing aggregates from raw event logs. This is accurate but computationally expensive ($O(n)$ per query) and lacks formal privacy guarantees.
    
    \item \textbf{Apache Druid:} Maintains immutable segments; deletions require segment rewrites. Not designed for real-time deletion propagation.
\end{enumerate}

These systems use \textbf{offline recomputation} for correctness but lack streaming efficiency and privacy guarantees. Our approach combines streaming sketches (KMV) with explicit tombstones and DP mechanisms, offering $O(k)$ memory, real-time updates, and formal $(\varepsilon, \delta)$-DP guarantees.

\subsection{Our Positioning}

Our project occupies the gap between theoretical DP continual release (which assumes exact sets) and production sketch-based systems (which lack privacy and deletion). We combine user-level DP mechanisms from the theoretical literature with deletion-friendly KMV sketches and a practical service interface, targeting GDPR-compliant DAU/MAU under real-time deletions.

\section{Hypothesis}
%==============================================================================

\textbf{We hypothesize that combining a user-level differentially private mechanism with a deletion-friendly distinct-count sketch (KMV) will yield DAU/MAU estimates whose median relative error is below 5\% on realistic workloads at privacy levels $\varepsilon \le 1.0$, while still correctly honoring all user deletion requests.}

\vspace{0.5em}
We decompose this into three concrete use cases:

\paragraph{Use Case 1: Streaming Distinct Counting with Deletions.}
\textbf{Hypothesis:} We argue that using a deletion-friendly KMV sketch instead of a traditional HLL allows accurate DAU/MAU estimation under user deletions, while still supporting efficient streaming updates with $O(k)$ memory for $k$-minimum-values sampling.

\paragraph{Use Case 2: Differential Privacy under Continual Observation.}
\textbf{Hypothesis:} We hypothesize that applying user-level DP with sensitivity 1 (via daily coalescing) and Rényi DP composition ensures that continual MAU/DAU releases protect privacy while maintaining low relative error ($<5\%$) for realistic $\varepsilon$ values.

\paragraph{Use Case 3: Combining DP with Deletion-Friendly Sketches.}
\textbf{Hypothesis:} We argue that integrating user-level DP mechanisms with a deletion-supporting KMV sketch and explicit tombstone propagation achieves both privacy guarantees and correct handling of "right to be forgotten" deletions, outperforming naive approaches that ignore deletions.

\section{Experimental Settings}

\subsection{Datasets and Workloads}

We evaluate our system on synthetic turnstile streams designed to mimic realistic app usage over a 30-day window ($T=30$). User populations are generated with configurable sizes and activity patterns:

\begin{itemize}[leftmargin=*]
    \item \textbf{Primary evaluation:} $N = 500$ users, 30 days, activity probability $p = 0.30$, deletion rate $q = 0.10$, generating approximately 5,800 events.
    \item \textbf{Larger scale test:} $N = 10{,}000$ users, 30 days, activity probability $p = 0.20$, deletion rate $q = 0.05$, generating approximately 71,000 events.
\end{itemize}

Each user $u$ is assigned an activity probability $p$ drawn from $\text{Beta}(0.5, 5.0)$ to reflect heavy-tailed engagement patterns (many casual users, few power users). For each day $d$, user activity is sampled as $\text{Bernoulli}(p_u)$; positive events $+u@d$ are emitted at random timestamps within the day.

Deletion requests are modeled by selecting a fraction $q$ of users uniformly at random. For each such user $u$, a deletion day $d_{\text{del}}$ is sampled from the latter half of the evaluation period, and negative events $-u@d$ are emitted for all previous active days $\le d_{\text{del}}$. This models GDPR-style erasure where a user requests complete removal of their historical activity.

\subsection{Algorithms and Baselines}

We compare three approaches:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Exact non-private baseline (SetSketch):} Python sets per day for DAU and rolling unions for MAU. This provides ground truth counts with zero approximation error but no privacy protection.
    
    \item \textbf{KMV sketch with DP:} Daily KMV sketches maintaining the $k=4096$ minimum hash values, with set-difference support for deletions. Laplace noise (for DAU) or Gaussian noise (for MAU) added at release time.
    
    \item \textbf{DP mechanism details:}
    \begin{itemize}
        \item DAU: Laplace mechanism with sensitivity $\Delta = 1$ (each user contributes at most 1 to any day's count).
        \item MAU: Gaussian mechanism with sensitivity $\Delta = 1$ and $\delta = 10^{-6}$, composed via Rényi DP across multiple releases.
    \end{itemize}
\end{enumerate}

\subsection{System Architecture and Algorithm}

Our implementation follows a modular pipeline architecture. Algorithm~\ref{alg:pipeline} describes the complete system flow.

\begin{algorithm}[H]
\caption{DP-DAU/MAU Pipeline with Deletion Support}
\label{alg:pipeline}
\begin{algorithmic}[1]
\Require Event stream $\mathcal{E}$, privacy parameters $(\varepsilon, \delta)$, sketch size $k$
\Ensure Differentially private DAU/MAU estimates

\Statex \textbf{// Initialization}
\State $\text{Ledger} \gets \text{SQLite database for activity log}$
\State $\text{Accountant} \gets \text{RDP privacy accountant}$
\State $\text{Snapshots} \gets \{\}$ \Comment{Day $\to$ sketch cache}
\State $\text{SaltManager} \gets \text{HMAC-SHA256 with 365-day rotation}$

\Statex
\Statex \textbf{// Event Ingestion}
\Function{IngestEvent}{$e = (u, \text{op}, d, \text{metadata})$}
    \State $\text{user\_root} \gets \text{HMAC}(\text{secret}, u)$ \Comment{Stable pseudonym}
    \State $\text{user\_key} \gets \text{HMAC}(\text{salt\_for\_day}(d), u)$ \Comment{Epoch-stable hash}
    
    \If{$\text{op} = ``+"$}
        \State $\text{Ledger.insert}(d, \text{user\_key}, \text{user\_root}, ``+")$
        \State $\text{Snapshots}[d].\text{dirty} \gets \text{True}$
    \ElsIf{$\text{op} = ``-"$}
        \State $\text{affected\_days} \gets \text{metadata.days} \cup \{d\}$
        \For{each $d' \in \text{affected\_days}$}
            \State $\text{key}' \gets \text{HMAC}(\text{salt\_for\_day}(d'), u)$
            \State $\text{Ledger.insert}(d', \text{key}', \text{user\_root}, ``-")$ \Comment{Tombstone}
            \State $\text{Snapshots}[d'].\text{dirty} \gets \text{True}$
        \EndFor
    \EndIf
\EndFunction

\Statex
\Statex \textbf{// Snapshot Building}
\Function{BuildSnapshot}{$d$}
    \State $\text{events} \gets \text{Ledger.fetch\_events}(d)$
    \State $\text{active} \gets \{\}$
    \For{each $(\text{op}, \text{key}) \in \text{events}$}
        \If{$\text{op} = ``+"$} $\text{active.add(key)}$
        \Else{} $\text{active.discard(key)}$
        \EndIf
    \EndFor
    \State $\text{sketch} \gets \text{KMVSketch}(k)$
    \For{each $\text{key} \in \text{active}$}
        \State $\text{sketch.add(key)}$
    \EndFor
    \State \Return $(\text{sketch}, |\text{active}|)$
\EndFunction

\Statex
\Statex \textbf{// DAU Query with DP}
\Function{GetDAU}{$d$}
    \If{$\text{Snapshots}[d].\text{dirty}$}
        \State $\text{Snapshots}[d] \gets \text{BuildSnapshot}(d)$
    \EndIf
    \State $\text{count} \gets \text{Snapshots}[d].\text{sketch.estimate}()$
    \State $\text{noise} \gets \text{Laplace}(0, 1/\varepsilon_{\text{DAU}})$
    \State $\text{Accountant.charge}(\varepsilon_{\text{DAU}}, 0, d)$
    \State \Return $\text{count} + \text{noise}$
\EndFunction

\Statex
\Statex \textbf{// MAU Query with DP}
\Function{GetMAU}{$d_{\text{end}}, W$}
    \State $\text{union} \gets \text{KMVSketch}(k)$
    \For{$d \gets d_{\text{end}} - W + 1$ \textbf{to} $d_{\text{end}}$}
        \If{$\text{Snapshots}[d].\text{dirty}$}
            \State $\text{Snapshots}[d] \gets \text{BuildSnapshot}(d)$
        \EndIf
        \State $\text{union.merge}(\text{Snapshots}[d].\text{sketch})$
    \EndFor
    \State $\text{count} \gets \text{union.estimate}()$
    \State $\sigma \gets \sqrt{2 \ln(1.25/\delta)} / \varepsilon_{\text{MAU}}$
    \State $\text{noise} \gets \mathcal{N}(0, \sigma^2)$
    \State $\text{Accountant.charge\_rdp}(\varepsilon_{\text{MAU}}, \delta, d_{\text{end}})$
    \State \Return $\text{count} + \text{noise}$
\EndFunction
\end{algorithmic}
\end{algorithm}

\section{Conclusion}
%==============================================================================

We have presented a complete implementation of a differentially private DAU/MAU counter that correctly handles user deletion requests. Our system achieves the stated hypothesis: combining KMV sketches with user-level differential privacy yields median relative errors below 2\% at privacy levels $\varepsilon \le 0.5$, while tombstone-based deletion propagation ensures that historical aggregates respect "right to be forgotten" requests.

\subsection{Achieving the Hypothesis}

Our experimental results confirm all three hypotheses:

\paragraph{Use Case 1 (Streaming Distinct Counting).} The KMV and Set sketches correctly support deletion via explicit tombstone events. The per-day snapshot architecture enables retroactive removal by marking affected days as "dirty" and rebuilding on next access. Memory usage scales as $O(k)$ for $k$-minimum-values, independent of user population.

\paragraph{Use Case 2 (Differential Privacy).} User-level DP with sensitivity 1 achieves relative errors of 0.9--2.0\% at $\varepsilon = 0.3$--$0.5$, well below the 5\% threshold. RDP composition provides 27\% tighter bounds than naive summation for MAU.

\paragraph{Use Case 3 (DP + Deletions).} The combined system correctly handles deletions while maintaining DP guarantees. Tombstone propagation ensures that historical aggregates reflect erasure requests, and the privacy accountant tracks budget independently of deletion activity.

\subsection{Limitations and Future Work}

\begin{itemize}[leftmargin=*]
    \item \textbf{Not flippancy-aware:} Our current implementation uses simple sensitivity-1 analysis rather than the full flippancy-aware mechanism of Jain et al. This is sufficient for our workloads where users are coalesced daily, but adversarial streams with high churn could benefit from explicit flippancy tracking.
    
    \item \textbf{Tree aggregation not implemented:} For very long time horizons (years of daily releases), tree-based mechanisms could reduce cumulative noise compared to our per-release approach.
\end{itemize}

\subsection{Contributions Summary}

The key contributions are:
\begin{enumerate}[leftmargin=*]
    \item A practical architecture combining streaming sketches with DP mechanisms;
    \item Epoch-stable hashing design that enables correct MAU deduplication;
    \item Explicit tombstone propagation for retroactive deletion;
    \item RDP-based privacy accounting with monthly budget enforcement;
    \item Comprehensive test suite with 82\% coverage and 33 passing tests.
\end{enumerate}

Our experimental results demonstrate that privacy-preserving analytics with deletion support is achievable at practical utility levels, addressing a real need for GDPR-compliant user counting in production systems.

\section{Privacy Parameters Configuration}
\label{appendix:privacy}

User-level $(\varepsilon, \delta)$-DP is adopted with the following configuration:

\begin{itemize}[leftmargin=*]
    \item \textbf{DAU:} $\varepsilon_{\text{DAU}} \in \{0.3, 0.5, 1.0\}$, $\delta = 0$ (pure DP via Laplace).
    \item \textbf{MAU:} $\varepsilon_{\text{MAU}} \in \{0.3, 0.5, 1.5\}$, $\delta = 10^{-6}$ (approximate DP via Gaussian).
    \item \textbf{RDP orders:} $\alpha \in \{2, 4, 8, 16, 32\}$ for tight composition.
    \item \textbf{Monthly budget caps:} $\varepsilon_{\text{total,DAU}} = 9.3$, $\varepsilon_{\text{total,MAU}} = 15.5$.
\end{itemize}

The RDP accountant tracks cumulative privacy loss across all releases within a month, converting RDP guarantees to $(\varepsilon, \delta)$ bounds using the standard conversion formula:
\[
\varepsilon = \min_{\alpha} \left( \frac{\rho(\alpha) - \log(\delta)}{\alpha - 1} \right)
\]
where $\rho(\alpha)$ is the Rényi divergence of order $\alpha$. Budget enforcement prevents releases that would exceed monthly caps.

\section{Deletion Correctness Verification}
\label{appendix:deletion}

We verified deletion semantics through unit tests and end-to-end evaluation:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Single-day deletion:} User Alice active on day 1, deletion processed on day 2 with \texttt{days: [day1]}. After rebuild, DAU(day1) correctly drops from 1 to 0.
    
    \item \textbf{MAU window deletion:} User Alice active on day 1, Bob on day 2. After deleting Alice, MAU(day2, window=2) correctly drops from 2 to 1.
    
    \item \textbf{Retroactive propagation:} Deletion tombstones are written to all specified historical days and trigger sketch rebuilds on next access.
    
    \item \textbf{Idempotency:} Processing the same deletion request twice does not corrupt data or double-count removals.
\end{enumerate}

All 33 unit tests pass, including 6 dedicated correctness tests for MAU uniqueness, hash stability, and retroactive deletion.

\section{Critical Implementation Decisions}
\label{appendix:decisions}

Several design decisions were critical for correctness:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Epoch-stable hashing:} We set \texttt{HASH\_SALT\_ROTATION\_DAYS = 365} to make it highly unlikely that any 30-day MAU window crosses an epoch boundary (probability $\approx 30/365 \approx 8\%$ for a randomly placed window; in practice we align epochs to calendar years). With a 30-day rotation, windows crossing epoch boundaries would double-count users. The epoch is computed as:
    \[
    \text{epoch}(d) = \lfloor \text{ordinal}(d) / 365 \rfloor
    \]
    
    \item \textbf{Sensitivity = 1:} MAU sensitivity is hardcoded to 1.0 rather than using \texttt{min(W\_BOUND, 1)}, avoiding potential under-noising if configuration allows $W_{\text{bound}} < 1$.
    
    \item \textbf{Explicit tombstones:} Rather than lazy deletion markers, we write explicit $-u@d$ events for each affected day. This ensures correct behavior regardless of query order and simplifies the rebuild logic.
    
    \item \textbf{Dirty flag propagation:} When a tombstone is written for a day, that day's snapshot is marked as "dirty" forcing a rebuild on the next query. This ensures deletions are reflected without requiring immediate recomputation.
\end{enumerate}
